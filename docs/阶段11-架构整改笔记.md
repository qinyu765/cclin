## Batch 1: TUI 多行编辑

### 问题

原始 TUI 输入框不支持手动换行，也不支持上下移动光标。用户只能通过粘贴来输入多行文本，体验极差。

### 核心挑战：终端是一维字符流

终端的输入本质上是一个**一维字符串** + **一个整数光标位置**，没有"行"和"列"的原生概念。要实现多行编辑，需要自己计算：

```
字符串: "hello\nworld"    光标位置: 8 (指向 'r')
终端显示:
  hello     ← 第 0 行，字符 0-4
  world     ← 第 1 行，字符 6-10
              光标在第 1 行第 2 列
```

### 实现方案

**文件**: `src/tui/composer_input.ts`

#### 1. 换行插入 (`insertNewline`)

最简单的函数——本质就是在光标位置插入 `\n`：

```typescript
export function insertNewline(value: string, cursor: number): EditorBuffer {
    return insertAtCursor(value, cursor, '\n')
}
```

复用了已有的 `insertAtCursor`，它已经处理了代理对安全和换行符规范化。

#### 2. 上下移动光标 (`moveCursorUp` / `moveCursorDown`)

这是最复杂的部分。思路是利用已有的 `getWrappedCursorLayout()` 函数。

这个函数的作用是：给定字符串、光标位置和终端宽度，计算出所有视觉行的信息：

```typescript
type WrappedCursorLayout = {
    lines: WrappedCursorLine[]  // 每行的文本和起止字符索引
    row: number                  // 光标所在的视觉行号
    cursorInRow: number          // 光标在行内的偏移
}
```

有了这个布局信息，`moveCursorUp` 的实现就很直观：

```typescript
export function moveCursorUp(value: string, cursor: number, columns: number): number {
    const layout = getWrappedCursorLayout(value, cursor, columns)
    if (layout.row <= 0) return 0  // 已在第一行，跳到最前
    const targetRow = layout.row - 1
    const targetLine = layout.lines[targetRow]
    // 保持列偏移不变，但 clamp 到目标行长度
    const targetOffset = Math.min(layout.cursorInRow, targetLine.text.length)
    return clampCursorToBoundary(value, targetLine.start + targetOffset)
}
```

**关键设计点**：
- 使用 `Math.min(cursorInRow, targetLine.text.length)` 实现"列位置保持"——如果上一行比当前行短，光标停在行尾
- `clampCursorToBoundary` 确保光标不会落在代理对的中间（emoji 等 UTF-16 双字节字符）

#### 3. 删除到行首 (`deleteToLineStart`)

类似 Bash 的 `Ctrl+U`，但要感知多行：

```typescript
export function deleteToLineStart(value: string, cursor: number): EditorBuffer {
    const lastNewline = value.lastIndexOf('\n', cursor - 1)
    const lineStart = lastNewline === -1 ? 0 : lastNewline + 1
    if (cursor === lineStart && lastNewline >= 0) {
        // 光标在行首时：删除换行符，合并上一行
        return { value: value.slice(0, lastNewline) + value.slice(cursor), cursor: lastNewline }
    }
    // 正常情况：删除光标到行首的内容
    return { value: value.slice(0, lineStart) + value.slice(cursor), cursor: lineStart }
}
```

#### 4. 快捷键绑定 (`input.tsx`)

在 Ink 的 `useInput` 钩子中分发：

```typescript
useInput((input, key) => {
    // Alt+Enter / Ctrl+J → 插入换行
    if ((key.meta && key.return) || (key.ctrl && input === 'j')) {
        const result = insertNewline(value, cursor)
        // ... 更新状态
    }
    // ESC → 清空输入
    if (key.escape) {
        setValue(''); setCursor(0)
    }
    // ↑↓ 箭头 → 多行导航
    if (key.upArrow) {
        setCursor(moveCursorUp(value, cursor, columns))
    }
})
```

**学习要点**：
- 终端不区分 `Shift+Enter` 和 `Enter`——它们发送相同的字节 `\r`。这就是为什么选择了 `Alt+Enter` 作为换行键
- `key.meta` 在 Ink 中对应 Alt 键（macOS 是 Option）
- `Ctrl+J` 是 ASCII 的 Line Feed (0x0A)，作为 Alt+Enter 的备选

## Batch 2: 配置管理迁移（TOML）

### 问题

原来使用项目根目录的 `.env` 文件存放 API Key，存在两个严重问题：
1. **安全隐患**：`.env` 在项目仓库内，容易意外 commit 到 Git
2. **能力有限**：`.env` 只支持 `KEY=VALUE` 平铺结构，无法表达嵌套配置

### 设计：三层优先级合并

参考 Claude Code 和 Cursor 的配置方案，设计了三层覆盖机制：

```
默认值 (代码硬编码)           ← 最低优先级
  ↑ 被覆盖
TOML 文件 (~/.cclin/config.toml)
  ↑ 被覆盖
环境变量 (OPENAI_API_KEY 等)  ← 最高优先级（向下兼容）
```

**为什么保留环境变量覆盖**？CI/CD 环境和 Docker 容器通常通过环境变量注入密钥，不应强制依赖文件。

### 实现

#### 类型定义 (`src/config/types.ts`)

```typescript
export type LLMProviderType = 'openai' | 'anthropic' | 'gemini'

export type CclinConfig = {
    llm: {
        provider: LLMProviderType
        api_key: string
        base_url: string
        model: string
    }
    approval: { policy: ApprovalPolicy }
    context:  { window: number; compact_threshold: number }
}
```

同时导出 `DEFAULT_CONFIG` 常量，作为合并的基准。

#### 加载器核心流程 (`src/config/loader.ts`)

```
1. 读取 ~/.cclin/config.toml
  → 成功：parseToml → tomlToConfig → 得到部分配置
  → 文件不存在(ENOENT)：创建模板文件（首次引导）
  → 解析失败：静默跳过，使用默认值

2. mergeConfig(DEFAULT_CONFIG, fileConfig)
  → 对每个嵌套对象做 spread 合并

3. applyEnvOverrides(config)
  → OPENAI_API_KEY 覆盖 config.llm.api_key
```

**为什么选 TOML 而不是 JSON/YAML？**

| 格式 | 优点 | 缺点 |
|------|------|------|
| JSON | 无需额外依赖 | 不支持注释！配置文件必须有注释 |
| YAML | 支持注释 | 缩进敏感，容易写错 |
| **TOML** | **注释 + 类型明确 + 结构清晰** | 需要引入 parser |

选择 `smol-toml`（~3KB gzip），纯 JS 实现，无需编译。

**学习要点**：
- `{ ...base, ...override }` 只做浅合并，嵌套对象需要逐层展开
- 首次引导（First-run onboarding）是 CLI 工具的重要 UX 细节

## Batch 3: 系统提示词增强

### 问题

原始 prompt.md 只有 65 行，简短地描述了 Agent 身份和可用工具。评审意见指出：生产级 Agent 的系统提示词通常有 500-1000+ 行，涵盖角色定位、约束条件、工具使用说明和安全策略。

### 参考：Claude Code 的提示词结构

通过研究 `claude-code.md`（1490 行），提炼出关键模块：

```
1. 身份声明 — "You are Claude, a powerful AI assistant..."
2. 风格约束 — 简洁、客观、无时间估计
3. 任务指导 — 读前写、避免过度工程
4. 工具使用策略 — 优先专用工具，并行独立操作
5. 环境安全 — 非沙盒警告、Git 安全协议
6. 项目上下文 — AGENTS.md 读取规则
```

### 实现

重写后的 `prompt.md` (99 行) 包含以下节：

| 节 | 内容 | 效果 |
|---|---|---|
| Identity | 角色声明 + 安全拒绝策略 | Agent 知道自己能做什么不能做什么 |
| Session Context | `{{date}}`/`{{user}}`/`{{pwd}}`/`{{platform}}` | Agent 感知当前环境 |
| Tone and Style | 简洁、客观、不估时间 | 减少废话，提高输出质量 |
| Before Writing Code | 先读后写、理解模式 | 减少错误修改 |
| Avoid Over-Engineering | 6 条反过度工程守则 | 防止 Agent 画蛇添足 |
| Tool Usage Policy | 工具优先、并行执行 | 提高效率 |
| Working Environment | 非沙盒警告 + Git 安全 | 防止破坏性操作 |

新增 `{{platform}}` 模板变量（`prompt.ts` 中添加 `process.platform + os.release()`），让 Agent 知道运行在什么操作系统上。

**学习要点**：
- 系统提示词是 Agent 行为的"宪法"——越精确，输出越可控
- "反过度工程"是关键约束，否则 Agent 会不停重构你的代码
- 模板变量让同一份提示词适配不同环境

## Batch 4: 上下文防爆改进

### 问题

虽然已有上下文压缩机制（Phase 6），但它只在总 token 数超阈值时触发。评审指出：**上下文暴涨的根源在于工具输出**，一次 `read_file` 读取大文件就可能注入数万 token，远超压缩能力。

### 思路：在源头控制，而不是在下游补救

```
                    ┌─── 源头控制（Batch 4）
                    │   • read_file 行数限制
                    │   • list_directory 噪声过滤
                    ↓
用户输入 → Agent → 工具调用 → 工具输出 → 历史积累
                                               ↓
                              ┌─── 下游补救（Phase 6）
                              │   • 压缩保留近期消息
                              ↓
                          压缩后历史
```

### 实现

#### 1. `read_file` 行数限制 (`src/tools/read-file.ts`)

```typescript
const DEFAULT_LINE_LIMIT = 2000

// 在 execute 函数中：
const lines = content.split('\n')
if (lines.length > lineLimit) {
    const truncated = lines.slice(offset, offset + lineLimit).join('\n')
    return {
        output: truncated + `\n\n--- Truncated: showing ${lineLimit} of ${lines.length} lines. `
             + `Use offset/limit to read remaining. ---`
    }
}
```

**设计考量**：
- 不直接截断字节，而是按行截断——保证每行内容完整
- 截断时在末尾附加提示，告知 Agent 可以用 `offset`/`limit` 参数分段读取
- Agent 通过提示词知道"大文件应分段读取"

#### 2. `list_directory` 噪声过滤 (`src/tools/list-directory.ts`)

```typescript
const NOISE_DIRS = new Set([
    'node_modules', '.git', '.next', '.nuxt', 'dist',
    'build', '.cache', '__pycache__', '.tox', 'venv',
    '.venv', 'coverage', '.nyc_output', '.turbo',
])

// 在读取目录后过滤：
entries = entries.filter(entry => !NOISE_DIRS.has(entry.name))
```

这些目录通常包含数万个文件，列出它们既无意义又浪费上下文。

#### 3. 压缩保留近期消息 (`src/runtime/compaction.ts`)

原有压缩策略：把所有历史消息压缩为一条摘要，只保留 system 消息。问题是 Agent 会丢失刚才的对话上下文。

改进：引入 `COMPACTION_TAIL_WINDOW`，压缩后保留最近 N 条消息：

```typescript
const COMPACTION_TAIL_WINDOW = 6

function buildCompactedHistory(
    systemMsg: ChatMessage,
    summary: string,
    originalHistory: ChatMessage[],
): ChatMessage[] {
    // 取最后 N 条消息（不含 system）
    const nonSystem = originalHistory.filter(m => m.role !== 'system')
    const tail = nonSystem.slice(-COMPACTION_TAIL_WINDOW)

    return [
        systemMsg,
        { role: 'user', content: `<context_summary>\n${summary}\n</context_summary>` },
        { role: 'assistant', content: 'Understood. I have the conversation context.' },
        ...tail,  // 保留最近的消息
    ]
}
```

**为什么是 6 条**？ 通常一次完整的工具交互是 3 条消息（user → assistant(tool_call) → tool），保留 6 条确保至少有 2 轮完整交互的上下文。

**学习要点**：
- "防爆"比"补救"更重要——在源头限制输出远比压缩算法优化有效
- 截断必须提供"怎么看到剩余部分"的提示，否则 Agent 不知道信息不完整
- 保留尾部消息是对话连续性和压缩效率的平衡

## Batch 5: Provider 抽象层

### 问题

原来的 `client.ts` 直接硬编码了 OpenAI SDK 调用。虽然 OpenAI-compatible API（如 DeepSeek、NewAPI）可以通过修改 `base_url` 接入，但 Anthropic 和 Gemini 使用完全不同的 SDK 和消息格式，无法通过换 URL 解决。

### 设计模式：接口 + 注册表（Registry）

这是经典的**策略模式（Strategy Pattern）**的变体：

```
              LLMProvider (接口)
              ┌──────────────────┐
              │ name: string     │
              │ createCallLLM()  │──→ 返回标准 CallLLM 函数
              └──────────────────┘
                    ▲   ▲   ▲
                    │   │   │
         ┌──────────┤   │   ├──────────┐
         │          │   │   │          │
   OpenAIProvider  (未来)  (未来)
                 Anthropic  Gemini
                 Provider   Provider

   providerRegistry: Map<string, () => LLMProvider>
```

### 实现

#### 1. Provider 接口 (`src/llm/provider.ts`)

```typescript
export interface LLMProvider {
    readonly name: string
    createCallLLM(config: ProviderConfig): CallLLM
}
```

只有两个成员：一个标识名，一个工厂方法。`CallLLM` 是项目已有的标准签名 `(messages, onChunk?) => Promise<LLMResponse>`，所以对调用方完全透明。

#### 2. 注册表

使用 `Map<string, () => LLMProvider>` 存储工厂函数（懒加载）：

```typescript
const providerRegistry = new Map<string, () => LLMProvider>()

export function registerProvider(name: string, factory: () => LLMProvider): void {
    providerRegistry.set(name, factory)
}

export function createProvider(type: LLMProviderType): LLMProvider {
    const factory = providerRegistry.get(type) ?? providerRegistry.get('openai')
    if (!factory) throw new Error(`No provider for "${type}"`)
    return factory()
}
```

**为什么用工厂函数而不是直接存实例？** 因为 Provider 可能需要在创建时初始化资源（如 SDK 实例），懒创建避免不必要的开销。

#### 3. OpenAI Provider (`src/llm/client.ts`)

原来的 `createLLMClient()` 函数被重构为 `OpenAIProvider` 类：

```typescript
class OpenAIProvider implements LLMProvider {
    readonly name = 'openai'

    createCallLLM(config: ProviderConfig): CallLLM {
        const client = new OpenAI({ apiKey: config.apiKey, baseURL: config.baseURL })
        // 返回闭包，捕获 client 和 config
        return async (messages, onChunk) => { /* ... 原有逻辑 ... */ }
    }
}

// 模块加载时自动注册
registerProvider('openai', () => new OpenAIProvider())
```

**自动注册**：`import './client.js'` 时，模块顶层代码立即执行 `registerProvider`，无需手动初始化。

#### 4. 入口调用 (`src/index.ts`)

```typescript
import { createProvider } from './llm/provider.js'
import './llm/client.js'  // 触发 OpenAIProvider 自动注册

const provider = createProvider(config.llm.provider)  // 'openai'
const callLLM = provider.createCallLLM({
    apiKey: config.llm.api_key,
    baseURL: config.llm.base_url,
    model: config.llm.model,
})
```

调用方不再直接依赖 `client.ts` 的具体实现，只依赖 `provider.ts` 的接口。

### 扩展新 Provider 的步骤

未来要加 Anthropic 支持，只需：

1. 创建 `src/llm/anthropic.ts`
2. 实现 `AnthropicProvider implements LLMProvider`
3. 底部 `registerProvider('anthropic', () => new AnthropicProvider())`
4. 在 `index.ts` 加一行 `import './llm/anthropic.js'`
5. 用户在 config.toml 写 `provider = "anthropic"` 即生效

**零修改**：不需要改 provider.ts、index.ts 的逻辑或任何 if/else 分支。

**学习要点**：
- 策略模式的核心价值：**新增策略不修改已有代码**（开闭原则）
- 模块副作用注册（`import` 触发注册）在 Node.js 生态中很常见（如 Passport.js 的策略注册）
- 工厂函数 vs 直接实例：前者支持懒加载和独立配置

## 总结：整改前后对比

| 维度 | 整改前 | 整改后 |
|------|--------|--------|
| 输入体验 | 单行，无法换行 | 多行编辑，Alt+Enter/ESC/↑↓ |
| 配置管理 | `.env` 在项目内 | `~/.cclin/config.toml`，三层合并 |
| 系统提示词 | 65 行，功能简述 | 99 行，涵盖安全/风格/工具策略 |
| 上下文保护 | 仅压缩 | 源头限制 + 压缩保留近期消息 |
| LLM 后端 | 硬编码 OpenAI | Provider 接口 + Registry 可扩展 |

**核心设计原则**：
1. **安全性**：密钥不入库，操作提醒非沙盒
2. **可扩展性**：接口 + 注册表，新增不改旧
3. **防御性**：在源头控制输出，而非依赖下游补救
4. **用户体验**：首次引导、快捷键、截断提示
